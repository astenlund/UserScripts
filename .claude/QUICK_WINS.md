misleads harder than a coarse one that holds.

## trakt_improved.user.js

- **Write-triggered membership refresh can read server-cache-stale list items.** Observed live 2026-07-28: the corrector sweep fetched `/users/me/lists/{id}/items` about 2s after a successful add and got a response not yet reflecting the write, so the optimistic filled icon reverted to outline until a later interaction healed it. Adjacent to the BUGS.md entry "Cross-tab list adds miss the fade treatment until it eventually self-heals", which covers the out-of-tab side of the same server-cache staleness. Since quick-list-fade-toggles shipped (Trakt Improved 1.22), quick-list membership fades ride the listed record's `fadeSlugs` (the quick lists are carved out of `counts`, so the threshold-2 path is not involved for these writes), and fade-on-list-pages (1.21) renders fades on list surfaces too; a stale corrector read therefore reverts the item's quick-category fade on every fade-active surface, /discover included, not just the toggle icon; see the Interactions sections in `features/fade-on-list-pages.md` and `features/quick-list-fade-toggles.md`. **Design settled 2026-08-02**, scoped to the script's own quick-toggle writes (native app writes keep current timing: the fetch hook cannot know their expected end state, so a blind settle delay is the only timing lever for them, rejected as a guess against unbounded cache lag; the truncate feature's bulk remove on the Uninterested list is the one other script-own write path and stays deliberately unledgered, since it applies no optimistic patch to defend and its own stale-sweep exposure predates this design and is unchanged by it):
  - **Settle bump.** New constant `WRITE_SETTLE_MS = 2000` replaces `MUTATION_SETTLE_MS` in both places the write-triggered flavor of `refreshMembership` uses it: the outer delay before forcing the sweep, and the coverage check (`sweepStartedAt < settledAt + WRITE_SETTLE_MS`). `notifyMutation` keeps `MUTATION_SETTLE_MS` at 1000ms. Honest reach: `notifyMutation` also feeds this engine (the `forceRefresh` mutation callback), and every surface with an active membership consumer launches the first post-write sweep at ~1s regardless of the bump: the fade scan on fade-active surfaces, the toggles feature's own menu-flavor `refreshMembership()` (via `refreshEntryStates`) on summary pages. On those surfaces the bump does not delay the first sweep; on fade-inactive card surfaces (home lanes, /watchlist, search results), where the dismissed popup leaves no membership consumer behind, the write-triggered sweep IS the first sweep and the bump delays it to 2s, exactly its purpose. Everywhere else its contribution is that the write-triggered forced corrector runs at 2s (one more second of server catch-up before an authoritative patch-or-agree pass) and that the widened coverage check refuses to count a pre-2s sweep as covering the write, guaranteeing a post-settle sweep exists. One write can thus produce two early sweeps (~1s and ~2s), each potentially a suspect commit; the retry rules below own that. 2000ms is a deliberately modest value: the observed staleness already reached ~2s and the lag is unbounded, so no settle value is sufficient alone; the ledger below is the actual defense, and the bump just cheapens the cases where the forced sweep is first. The other obvious alternative, a cache-defeating corrector read (unique query param or no-cache headers), was rejected untested: the ledger is lag-agnostic and assumes nothing about which cache layer serves the stale data, while a buster depends on undocumented Trakt/CDN cache keying and cannot reach server-internal replication lag; the 2026-07-28 stale response answered a fetch issued fresh ~2s post-write, so client request shape was already not the limiter.
  - **Confirmed-write ledger.** In-memory `Map` inside the membership engine, value `{name, slugKey, add, confirmedAt, markers}`, where `markers` is the `currentMarkers()` snapshot captured at note time (reconciliation and the drop rule read fields off the value, never parse the key); the key `` `${name}:${slugKey}` `` is an opaque dedup handle so the latest write to the same item wins (`slugKey` itself contains a colon, so the key is not two-way parseable by design). New surface `quickLists.noteConfirmedWrite(name, slugKey, add)`; `performToggle` calls it only on body-judged success. Placement note: the existing post-write block (`notifyMutation`, `bumpInvalidationMarker`, `refreshMembership`) runs unconditionally after `postToggle` settles, so the new call needs its own explicit `if (ok)` gate, placed after the existing `bumpInvalidationMarker()` call (the entry's captured marker snapshot must include this write's own bump) and before the `refreshMembership({ writeTriggered: true })` call. Other writers always win, via both foreign-write signals the engine has. Same-tab native writes: the page fetch hook's successful-write branch calls a new `quickLists.dropConfirmedWrites()`, emptying the ledger (the response arrives in real time, so it is always later than any confirmed entry). Other-tab writes: marker movement, judged per entry against the entry's own captured snapshot, NOT against the engine's committed snapshot; `markersChanged()` reports movement since the last committed sweep, so an unabsorbed bump that predates the write (typical on surfaces where sweeps are rare) would otherwise read as foreign and silently kill protection for a later, authoritative write with no retry scheduled. Instead, `noteConfirmedWrite` captures `currentMarkers()` into the entry, and the sweep drops, before reconciling, exactly the entries whose captured snapshot differs from live markers, excluding `SELF_MARKER_KEY` when its live value equals this tab's own tracked `selfMarkerValue` (a later same-tab quick toggle must not read as foreign to earlier entries). The exclusion alone would let this tab's next bump overwrite, and thereby erase, the evidence of a foreign bump that landed since its last one, so `bumpInvalidationMarker` reads the live key before overwriting and calls `dropConfirmedWrites()` first when that value is not the tab's own tracked one: a foreign bump's evidence is only ever destroyed after it has been acted on. Neither signal says what changed, and the design never knowingly defends a script write against a later write made anywhere else; the residual blind spot is a foreign bump landing inside the read-then-write instant of this tab's own bump, accepted as unreachable in practice. The script's own same-tab writes trip neither signal: they use the sandbox fetch, which the hook never sees, and `performToggle`'s direct `notifyMutation()` call is not the hook and does not drop. The drop is deliberately coarse: it may abandon protection for an unrelated pending write, trading a rare transient revert for never fighting another writer. Tab-local and non-persisted on purpose: cross-tab clobbering stays with the adjacent BUGS.md entry, and a reload inside the trust window is left to self-healing.
  - **Commit-time reconciliation in `refresh()`.** When the `listed` fetch fulfills, before `cache.listed` is assigned: prune ledger entries older than `WRITE_TRUST_WINDOW_MS = 30_000` (checking each expiring entry against the fetched target first: when the target exists, judge via the pure comparison `target.slugs.includes(slugKey) !== add` rather than the mutating helper, and `warn()` if it expires still contradicted, meaning protection ran out with the server never catching up and the original stale-read bug recurred for that item; when the target is missing (null, the state the missing-target rule below keeps entries alive in), drop the entry with a `warn()` that it expired unverifiable; diagnostic only, no UI signal either way), then run `patchTargetMembership` (below) for each survivor against the fetched `targets[name]`. Missing target: skip, keep the entry until window expiry. Helper reports no change: fetched state agrees, drop the entry, server caught up. Helper reports a change: that is the contradiction signal, and the expected state is now patched onto the record pre-commit; flag the sweep suspect. The rest of the sweep commits normally with a fresh `fetchedAt` (the re-sweep below is the reconciler, not TTL staleness). Commit-time placement closes every post-confirmation fetch/write interleaving in one place, subsuming races the `pendingForcedRefresh` bookkeeping does not catch. Known transient hole, accepted: a sweep that commits inside the optimistic-patch-to-confirmation window (the `postToggle` network round trip) finds no ledger entry yet and can briefly revert the optimistic state; once the write confirms, the entry exists and the write-triggered sweep restores it (patch-on-top or caught-up data). Ledgering at optimistic-patch time instead was rejected because a failed write would then defend phantom state.
  - **Escalating re-sweep.** State: one `nextRetryDelay` (starts at 5000ms) and at most one pending retry timer. A suspect commit with no pending timer schedules a forced re-sweep after `nextRetryDelay` (at fire time: `pendingForcedRefresh` if a sweep is in flight, else `forceRefresh = true` plus `queueRefresh()`), then doubles `nextRetryDelay` (5s, 10s, 20s). A suspect commit while a timer is pending schedules nothing and does not double, so the two early sweeps one write can produce advance the ladder at most once. A new noted write resets `nextRetryDelay` to 5s and leaves any pending timer alone (the write's own write-triggered sweep already covers promptness). The ledger becoming empty (all entries dropped by agreement, expiry, or a foreign-write drop) cancels a pending timer. The 30s window terminates the loop: entries past it stop being defended, so a late retry commits server truth unconditionally; worst case is at most two early sweeps plus 3 retries. A suspect read is not a failure: it never touches `lastFailureAt`, backoff, or `rearmedRefresh`.
  - **Shared patch helper.** Extract `patchTargetMembership(target, slugKey, add)` from `applyListToggle`'s inline slugs/fadeSlugs set logic, with the exact-membership guard INSIDE the helper: when `add === target.slugs.includes(slugKey)` it returns false having touched neither set; otherwise it applies the set semantics to both `target.slugs` and `target.fadeSlugs` and returns true. The guard placement is load-bearing: `fadeSlugs` is a strict superset of `slugs` (a season entry contributes its parent show), so a guardless helper would strip a legitimately season-backed fade from freshly fetched server data on reconciliation's agree path and commit it with a fresh `fetchedAt`, a wrong un-fade with no reconciler for the full cache TTL. `applyListToggle` keeps its current no-op behavior by returning early when the helper returns false (no sets rebuild, no persist, no rescan), and the commit-time reconciliation uses the same return as its contradiction signal. Keeps the removal-direction approximation documented at `applyListToggle` in exactly one place.
  - **Contention with the quick-toggle reliability bug.** The open BUGS.md entry "Anticipated/Uninterested quick toggles rarely take effect, and failures are silent" is filed against the same functions this design edits (`performToggle`, `applyListToggle`), on the same two lists, and it distrusts exactly the body-judged `ok` signal the `if (ok)` ledger gate keys on: a wrongly-false `ok` leaves the design inert for that write, and a wrongly-true one records a phantom confirmed write that reconciliation then defends for up to the trust window. Landing order: this quick win first (mirroring the order recorded in `features/fade-on-list-pages.md` and `features/quick-list-fade-toggles.md` for the same contention), with e2e verification run against toggles that demonstrably work; if the bug bites during verification, diagnose it first. A later fix to how `ok` is judged is inherited automatically, since the gate reads the same variable. A mirror note belongs in the bug entry when this lands.
  - **Verification and landing.** E2e via namespaced injected build with the sandbox `fetchListedData` wrapped to simulate cache lag in both directions for ~15s: for an add-write, strip the just-written slug from both `slugs` and `fadeSlugs` of the fetched target; for a remove-write, inject it back into both. Observe per direction: icon/fade hold, escalating retries, reconciliation, and (with the wrap disabled) the agree path dropping the ledger entry with no retry. The simulation confirms the machinery, not the server: the claim that Trakt's real list-items cache catches up within the 30s trust window (and usually by the 2s settle) is owned by Trakt's servers; probe it with a real add and a real remove from each menu context (card popup and summary actions) against the live API with no simulated lag, watching each write for at least 40s (past the last revert-capable retry at ~37s) through the e2e build's window handle. Pass condition: the ledger entry drops via the agree path within the 30s window and the icon/fade never revert; "no revert" alone proves nothing, since the design defends the state for the full window either way. An entry that expires still contradicted refutes the claim and routes to correction, not to a probed marker (live-claim: probed 2026-08-03). Index-only entry, so the stamp-refresh half of live-claim handling is skipped. Bump `@version` to 1.26. No `Requires:` lines reference this entry, so no `Requires:` walk is needed.
